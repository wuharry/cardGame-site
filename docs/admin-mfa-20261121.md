## 第二輪：合法 QR 超過錯誤的大小限制

Supabase 使用 `goqrsvg` 將 QR 的黑白格逐格輸出為 SVG `<rect>`。以相同中文 issuer、`owner@example.test` 與公開假 seed 建立 77×77 格的測試圖，序列化後為 **452,088 字元**，超過原本的 200,000 上限。此為合成圖實測，沒有擷取正式 MFA 圖或金鑰。

`node scripts/test-admin-api.mjs` 在未修正程式上可重現相同 `AdminError`；修正將圖檔上限調整為 4,000,000 字元，足以容納最大 QR 版本的逐格表示。仍檢查 factor ID、secret 格式、SVG 根元素／MIME 與有限大小；仍僅以圖片顯示，不注入 HTML、不跳過驗證 App。

寄送頁另修正：重寄按鈕顯示剩餘秒數並在冷卻期間停用；修改信箱和重新寄送分開。重寄不先移除驗證碼欄位；送出驗證碼後清空欄位，避免後續步驟出錯時把已用過的碼原樣留下。

驗證：登入 API **60 項通過**（包含密碼／Email 兩條路徑的完整大小 QR，以及超上限拒絕）；TypeScript、ESLint、隔離正式建置與既有統計／官網桌面手機回歸通過。新增瀏覽器驗證完成桌面／手機的首次綁定、實際大 SVG 圖片解碼、重寄倒數、MFA 錯碼重試、重設密碼後回到登入。全部使用假資料及攔截的本機 HTTP，沒有向正式資料庫寫入測試資料；畫面在 `shots/auth-diagnosis-20261121`。

合成 QR 樣本在 `scripts/fixtures/admin-mfa-dense-qr.json`；矩陣使用 qrcode 8.2、H 級、byte mode 產生，SVG 採 goqrsvg／SVGo 的逐格格式；不宣稱 Python 編碼器與 Go 編碼器的黑白矩陣逐位一致。樣本只用於合法大小與圖像顯示回歸，不是正式帳號憑證。

## 第一輪修正紀錄

正式後台顯示「驗證 App 設定回覆不完整」。本機用 Supabase 的 SVG 產生器格式重現同樣錯誤：原本只接受以 `<svg` 開頭的文字，但 SVGo 會在 SVG 前加 XML 宣告和註解。

修正只將宣告、前置空白與註解排除於根元素檢查，保留原圖內容，仍透過編碼後的圖片 URL 顯示。非 SVG、錯誤 MIME 格式、超過上限及缺少有效 factor／secret 的回覆仍拒絕並登出。會員權限、信箱驗證、TOTP 驗證和新密碼規則不變。

驗證：修復前新增的真實回覆格式測試失敗；修復後登入 API **57 項通過**，TypeScript、ESLint 通過。隔離環境的正式建置、桌面／手機統計頁與管理介面、390／1440 寬度官網瀏覽器回歸均通過；畫面證據在 `shots/mfa-20261121`。瀏覽器測試使用替代後端回覆，沒有向正式資料庫寫入測試資料。

密碼重設由管理員本人完成信箱驗證、驗證 App 和新密碼輸入；本次沒有設定或接收使用者密碼。

來源：[Supabase MFA 產生流程](https://github.com/supabase/auth/blob/master/internal/api/mfa.go)、[SVGo 的 XML 前綴](https://github.com/ajstarks/svgo/blob/master/svg.go)。這些來源支持格式相容性的原因；實際登入成功仍須在部署後由管理員驗證。
